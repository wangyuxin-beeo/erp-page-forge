# 生成层：确定性优先，生成式兜底

> 2026-10-14 产品边界纠正：本文件旧的截图→PageSpec→A1–A6 适配描述仅为历史实现，不再用于截图创建模板。截图入口独立走 `/api/ai/analyze` 的 `mode:screenshot` → `/api/forge/screenshot` → `screenshot_render.py` → `verify_screenshot.py`，保存独立结构并复用；不补配方、不套骨架、不应用 premium。内置模板继续用 forge.py。结构断言通过不代表像素还原通过，视觉与业务交互必须人工复核。

> 这一层解决的是「慢、贵、每次不一样」。`SKILL.md` 是给模型读的规范，
> 而这里是**可执行的渲染路径** —— 同一份 `PageSpec` 渲染两次，结果逐字节一致。

---

## 1. 为什么要有这一层

让模型每次重新发明页面骨架，是最大的浪费。A1–A6 六个原型里，**结构、交互、样式几乎完全固定**，
差异只在字段与状态。所以分工应该是：

| 部分 | 谁来做 | 理由 |
|---|---|---|
| 页面骨架（布局、组件树、响应式断点） | **模板渲染**（确定性） | 可预测、可 diff、快、省 token |
| 交互接线（查询/重置/排序/分页/批量/抽屉） | **模板渲染** | 这些是规范铁律，不该每次重新生成 |
| 样式 | **模板 + 令牌注入** | 令牌是数据，直接替换即可 |
| 字段语义映射（"修改节点"用下拉还是标签） | **生成式** | 需要理解业务语义 |
| 命名、边界情况推导 | **生成式** | 需要判断力 |

## 2. 三条命令

```bash
# ① 生成：PageSpec → 可运行单文件 HTML
python build/forge.py --spec skill/spec/examples/license-approval.pagespec.json --out out/license.html
python build/forge.py --entity salesOrder --archetype A1 --out out/so.html   # 从配方快捷生成

# ② 反向工程：已有页面 → PageSpec（「照这个做，字段换成我的」）
python build/reverse.py --artifact templates/05-approval-inbox.html --out out/spec.json
python build/reverse.py --artifact <页面> --rename "出入库单据管理" --out out/new-spec.json

# ③ 验收：生成物回灌四类断言闸门（阶段一的通用校验器，不区分是谁生成的）
python build/verify_acceptance.py --spec out/spec.json --artifact out/so.html \
    --root <构建产物目录> --route <路由> --out out/acceptance.json
python build/build_report.py --report out/acceptance.json --out out/report.html
```

**反向工程是最被低估的一条入口**：社区里已有的示例就是最好的模板源。
用户不必从零描述，只要指着一个跑得好的页面说"照这个来"。抽出的 `PageSpec` 里
每个字段都标了 `provenance: inferred`，提醒用户"这是推断的，确认一下"。

## 3. 骨架覆盖情况（刻意不追求全覆盖）

| 原型 | 骨架 | 说明 |
|---|---|---|
| A1 管理列表页 | ✅ 完整 | 查询/工具条/排序/分页/批量/抽屉/汇总行 |
| A2 单据表单页 | ✅ 完整 | 字段分组/明细增删/数量×单价自动算/合计/必填校验/吸附动作条 |
| A5 审批工作台 | ✅ 完整 | 三栏/待办计数/审批轨迹/同意-驳回-转办/不可自审 |
| A3 / A4 / A6 | ⛔ 无骨架 | `forge.py` 会明确提示并**回退到生成式**（全量生成） |

**为什么不做全**：过度模板化会扼杀用户真正想要的变体。
骨架没覆盖时，`forge.py` 直接说清楚"这个原型请走全量生成"，而不是硬凑一个四不像。
这是设计上的逃生舱，不是能力缺口。

`PageSpec.custom` 是另一个逃生舱：模板表达不了的诉求写进 `custom`，
生成层就知道该整体回退，而不是把诉求悄悄丢掉。

## 4. 确定性是怎么保证的

1. **数据种子固定**：mock 数据的随机种子 = `sha1(页面名 | 实体名)`，与时间无关。
2. **产物不含时间戳**：产物头部只声明**依赖的规范版本**，不写生成时刻。
3. **样式来自令牌**：色值/圆角/字号由 `spec/tokens.json` 注入 CSS 变量，模板本身不写死字面量。
4. **排序稳定**：字典键按固定顺序遍历，不用 `set` 直接迭代。

验证方式：

```bash
for i in 1 2 3; do python build/forge.py --spec <spec> --out run$i.html; done
md5sum run*.html     # 三次应完全一致
```

## 5. 生成的产物长什么样

单文件 HTML，零依赖、断网可开。结构上分三块：

```
<head>
  ├─ 错误兜底脚本（初始化期异常写进 window.__PAGE_ERRORS__，便于验收定位）
  ├─ 依赖规范版本声明（注释）
  └─ <style> 令牌变量 + 基础样式（来自 spec/tokens.json + skeletons/base.css）
<body>
  ├─ <script>window.__MODEL__ = {...}</script>   数据与列/动作定义（JSON，可 diff）
  ├─ <script>通用运行时</script>                  格式化/Toast/抽屉/弹窗/分页器/列表能力
  ├─ 左侧导航 + 顶部工具栏
  └─ 正文（由对应骨架渲染：页面头 / 查询区 / 工具条 / 表格 / 分页器 …）
```

把**数据（`__MODEL__`）与渲染逻辑分离**，好处是变更可 diff：
改了哪个字段、加了哪个动作，一眼能看出来，而不是"整个文件都变了"。

## 6. 生成层的边界

- **接口层不生成**：只产出前端页面与 mock 数据，请求层留 `TODO`。
- **不做安全绕过**：审批/提交类动作保留人工确认环节（见 SKILL.md 第 9 节）。
- **不替代评审**：机械断言过得去 ≠ 业务上合理。第 8 节自检清单里
  「数据有没有业务故事」「术语是否一致」这些仍需人工判断。

## 7. 截图入口：用户丢一张图，要的是"准"

真实场景里最常见的提需求方式是**丢一张截图**（"照这个做"）。让 AI 直接照着图"画"一个页面，
问题是每张图结果都不一样、也没法验收。所以截图入口也压进同一套契约：

```
截图 ──多模态模型（看）──→ extract.json：页面名/列/控件/动作/状态/置信度/存疑项
     ──build/vision.py（算）──→ PageSpec（provenance = visual）
     ──build/forge.py（渲染）──→ 单文件 HTML
     ──验收（四类断言 + 视觉断言）──→ 验收报告
```

**分工是刻意的**：
- 模型负责"看得懂"（业务语义、字段含义、按钮归属哪个状态）
- 脚本负责"算得准"（像素锚点、契约校验、配方补全）

### 7.1 两个防止"不准"的机制

1. **提取结果必须标置信度**。低于 0.8 的自动进 `uncertain` 清单并打印出来，逼着人确认 —— 不悄悄用。
2. **提取结果要用配方补全**。截图看不出 `options` / 精度 / 单位，只能靠 `spec/recipes.json`。
   不补的后果很典型：枚举列全渲染成「—」、状态列只剩一个空心圆点 ——
   页面"看着像、内容是空的"，肉眼扫一眼未必发现。实测就是这么踩到的。

### 7.2 还有一层：输入体检

`python build/vision.py --image shot.png --check`

从像素里量出侧栏宽度 / 顶栏高度 / 主色 / 深色占比，若明显不像 ERP 后台
（量不到侧边栏、深色占比 <3%、识别不出主色），直接说"这张图可能不是后台截图"，
而不是硬着头皮生成一个错的。**先判断能不能做，再动手** —— 这是"不准确"的第一道闸门。

### 7.3 人工复核路径（Studio 工作台）：批量操作，不是一个个点

截图入口还有一条**人工兜底路径**：`studio/index.html`（本地工作台，`build/studio_server.py` 起服务）。
自动拆层识别不了的页面，用户自己框层标语义也能走到同一个 PageSpec。这条路径的体验按三条硬规则做：

1. **噪声层不进工作流**。图标、角标、装饰方块这类碎块自动标记为「装饰层」：不计入命名与 extract
   统计、图层列表默认折叠，面板上有「装饰 N」计数与「清装饰」一键清理。**要求用户逐个判断碎片
   是什么语义，本身就是设计的失败** —— 碎片不该参与计数。
2. **标注支持批量**。图层列表支持 Ctrl/Shift 多选；批量面板可一次改语义、按坐标顺序用逗号
   批量命名（列头从左到右）、批量移除。同类元素几十个时，逐个点是不可接受的。
3. **标注与 extract 双向同步，且生成入口不拦截**。改语义 / 批量命名后 extract.json 自动重算；
   点「生成页面」时若 extract 为空或不是合法 JSON，**自动按当前图层标注生成草稿**，而不是弹
   「不是合法 JSON」这种用户无从下手的报错。**识别不到表格 / 表头也照常生成** —— 前后端都不
   拦：前端没有可用结构时给一个最小骨架（archetype + 空 columns），后端 `vision.py` 把 columns
   从必填降为警告，由生成器用配方与占位补全（实测空 columns 也能渲染出带 12 行占位数据的
   通用骨架页面）。生成后再靠验收断言提示缺什么，而不是在入口处把用户挡死。

> 报错必须可操作。占位名（未命名的列头 / 字段）在日志里**明确计数**并指向「批量命名」，
> 而不是静默生成一个半成品 —— 用户要的是"哪一步缺什么"，不是一句 JSON 解析失败。

### 7.4 视觉断言（第 5 类断言）

`python build/verify_visual.py --expect <原截图> --actual <生成物截图>`

零依赖解析 PNG（标准库 zlib + 手写反过滤），把两张图做**结构化比对**：

| 维度 | 判据 | 为什么盯它 |
|---|---|---|
| 左侧导航宽度 | 差 ≤10px | 差 20px 一眼就能看出"不是同一个系统" |
| 顶部工具栏高度 | 差 ≤8px | 同上 |
| 主色 | RGB 色距 ≤46 | 主色偏一点，整页观感就变了 |
| 画布宽高比 | 差 ≤0.06 | 判断是否同一版式 |
| 深色像素占比 | 差 ≤5% | 校验"深色侧栏 + 浅色卡片"的整体版式 |

输出**还原度评分**（0–100）。实测同一页面自比对为 100/100，差异全为 0。

> 注意：像素比对只看**版式与配色**。文本内容（列头、按钮、状态枚举）要靠契约断言与
> 「渲染后空列」断言核对 —— 两者缺一不可。
> 实测教训：像素指标 100/100 的那一版，状态列其实是空的。所以第 5 类断言
> **不能替代**前四类，只能补充。

## 8. 视觉还原：用户截图上的配色与尺寸，也要跟过来

识别出"页面上有什么"只是第一步。用户说"按这张图做"时，他在意的还有**长什么样** ——
主色是青绿不是蓝、侧栏 240px 不是 216px、顶栏 48px 不是 56px。
这一层靠 `PageSpec.tokens` 注入，不走模型发挥。

### 8.1 三个环节

| 环节 | 工具 | 产出 |
|---|---|---|
| 量 | `verify_visual.py --tokens` | 主色 / 侧栏底色 / 页底色 / 卡片色 / 侧栏宽 / 顶栏高 |
| 注入 | `forge.py` 的 `merge_tokens()` | 覆盖 Skill 默认令牌，并派生浅底、深色、hover、选中态 |
| 验 | `verify_visual.py --expect --actual` | 还原度评分（硬性视觉项） |

### 8.2 派生：量不到的那一半怎么补

截图只能量到主色与侧栏底两三个色值，产物却需要十来个。缺的按业界通行比例推：

| 派生项 | 规则 |
|---|---|
| `brandSoft` | 主色与白混 90% |
| `brandDark` | 主色与黑混 18% |
| `sidebarHover` | 侧栏底与白混 7% |
| `sidebarActive` | 侧栏底与主色混 28% |
| `sidebarText` / `sidebarTextStrong` / `sidebarBorder` | **按侧栏底亮度翻转**：亮底用深字深边框，暗底用浅字 |

最后一条是"浅色侧栏"能看的前提。侧栏是白的还沿用 `#C7CEDE` 浅灰字，整条导航就是浅字浅底。

### 8.3 侧栏宽度的两种量法

- **深色分界法**：从 x=0 往右找第一处"连续 8px 变亮"。对深色侧栏最准。
- **贯穿边框法**：找一条贯穿 ≥80% 探测高度的垂直细线。浅色侧栏（整片都亮）只能靠它。

两道保护都是踩出来的：

1. 分界法必须跳过深色底上的亮色文字，否则 216px 会量成 309px。
2. 结果 <100px 一律判为误判并交给边框法 —— 浅色侧栏的**选中项色块**会让分界法在色块左缘量出 3px。

### 8.4 不能从像素还原的，要明说

`--tokens` 的输出带一份 `cannotReproduce` 清单：圆角半径、阴影、字号与字体、
行高与组件密度、列宽比例、图标风格。抗锯齿、压缩噪声、运行时布局都不支持可靠反推。

报"能还原"却交出一个不像的页面，比直说"这几项我量不出来"伤害大得多。

### 8.5 边界（当前不做）

- 按钮可见性只按**状态**控制，不支持按其他字段值分支
  （原图"入库单显示上架、出库单显示出库"这类会同时列出两个）。
- 分页总数按实际生成行数显示，不还原原图的虚高总数 —— 显示 36 条却只有 12 行，翻页会翻到空页。
- 状态一律用统一胶囊，不跟随原图的彩色文字（业务规范层服从 Skill）。

### 8.6 最容易忽略的一课

把外部截图还原到像素指标 100 分的那一版，内容层仍有 6 处不对：品牌名还是自家的、
枚举列整列空白、状态只剩圆点、单号是占位符、往来单位是「示例-52」、状态值用的是配方预设。
**修完这 6 项，像素评分一点没变。**

所以：用户抱怨"生成得不准确"，八成不是配色问题，而是**内容有没有接上**。
视觉断言与内容断言管的是两件不同的事，谁也不能替代谁。
