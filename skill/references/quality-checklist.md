# 质量自查清单（可执行版）与打分标准

> 用法：页面生成后，**逐条对照下面的"检查动作"实际点一遍**，不要凭印象打勾。
> 本清单用于页面效果验证与人工评审。

## A. 结构完整（4 项）

| # | 检查动作 | 通过标准 |
|---|---|---|
| A1 | 对照 `page-archetypes.md` 数区块 | 原型的必备区块一个不少、顺序未变 |
| A2 | 看面包屑 | 三级：模块 / 菜单 / 当前页，当前页加粗 |
| A3 | 筛选一个不存在的关键词 | 出现空状态占位 + "清空筛选条件"按钮，不是白屏 |
| A4 | 页脚 | 有"演示用虚构数据"免责说明 |

## B. 数据可信（4 项）

| # | 检查动作 | 通过标准 |
|---|---|---|
| B1 | 用计算器把明细加一遍 | 与页面合计完全一致（分位不差） |
| B2 | 检查余额列 | 逐行累加自洽 |
| B3 | 抽查库存/额度状态与数值 | 数值与状态语义一致（低于安全库存不能显示"充足"） |
| B4 | 全页搜索真实企业名/真名/真实手机号 | 0 命中 |

## C. 交互真实（6 项）

| # | 检查动作 | 通过标准 |
|---|---|---|
| C1 | 输入筛选条件点查询 | 行数或内容变化 |
| C2 | 点表头排序 | 数据重排 + ▲▼ 指示切换 |
| C3 | 点分页页码 | 内容变化且显示"第 X-Y 条 / 共 N 条" |
| C4 | 勾选 2 行 | 工具条显示"已选 2 项"，批量按钮由禁用变可用 |
| C5 | 点行内"提交/审核" | 状态标签与可用按钮同步变化 |
| C6 | 任意按钮 | 均有点击反馈（Toast / 状态变化 / 弹窗），无"死按钮" |

## D. 视觉规范（4 项）

| # | 检查动作 | 通过标准 |
|---|---|---|
| D1 | 全局搜索色值 | 只出现设计令牌内的值（无 `#333` `#409EFF` `blue`） |
| D2 | 看表格对齐 | 金额数量右对齐、状态日期居中、文字左对齐 |
| D3 | 数主按钮个数 | 每屏 ≤1 个主色实心按钮 |
| D4 | 窗口缩到 1280px | 无横向滚动条 |
| D5 | 找 `2026-09-17` 与 `¥1,286,400.00` | 单行显示，未被折成两行（数字列有 `white-space:nowrap`） |
| D6 | 看含表格的栅格弹性列 | 写的是 `minmax(0,1fr)`，不是裸 `1fr`（裸 `1fr` 会被表格顶开导致整页溢出） |

## E. 工程与合规（3 项）

| # | 检查动作 | 通过标准 |
|---|---|---|
| E1 | 断开网络后打开文件 | 完全正常渲染与交互 |
| E2 | 查看源码 | 无 CDN、无外部请求、无外链字体图标 |
| E3 | 检查是否存在自动提交/自动执行 | 生成类动作均有人工确认环节 |

## F. 跨栈适配（3 项）

> 仅当目标是一个**已有项目**时需要检查。产出独立单文件 HTML 时可跳过本组。

| # | 检查动作 | 通过标准 |
|---|---|---|
| F1 | 翻本次生成的记录 | 生成前**实际读过**目标项目的 `package.json`、构建配置、目录树与 2–3 个现有源文件，并写出了「项目约定画像」 |
| F2 | 全局搜索色值 | 目标项目已有令牌时，产物里只出现该项目的令牌变量，**零 Skill 原色值残留**（如 `#2B5CFF`）、零硬编码 hex |
| F3 | 跑目标栈的验证命令 | React → `npm run build` 通过；Vue/TS → `vue-tsc --noEmit` 零错误 + build 通过；并做过一次真实渲染检查（零脏值、零溢出） |

**总计 26 项**（结构 4 + 数据 4 + 交互 6 + 视觉 6 + 工程合规 3 + 跨栈适配 3）。
与 `SKILL.md` 第 8 节的 23 项主清单一一对应，本表拆得更细、每条都给了可执行动作。合格线：全部通过。

> **D5 / D6 是第一轮实测补出来的两条。** 生成 A1 时后段行出现 `undefined`（mock 数组长度不一致），
> 生成 A5 时出现 142px 横向溢出（表头 `nowrap` 顶开了裸 `1fr`）——
> 这两类问题靠"看代码"很难发现，**必须真实渲染 + 缩到 1280px 才发现得了**。
> 因此 `build/render_check.py` 把这两项做成了自动检查。

> **F 组是第二轮实测（跨技术栈）补出来的。** 把同一套需求从 React 19 换到 Vue 3 + TS + Pinia 重做一遍，
> 暴露出三件事：不探测就生成必然对不上项目约定；项目已有自己的设计令牌时硬套 Skill 色值会"一眼看出是外来的"；
> 类型检查与真实渲染都必须真跑一遍才算交付。因此 `build/verify_vue_render.py` 把渲染级检查做成了可复用工具。

## 打分标准（100 分制，用于横向对比多个生成结果）

| 维度 | 分值 | 评分要点 |
|---|---|---|
| 结构完整 | 15 | 原型骨架齐全、层级清晰 |
| 数据可信 | 20 | 自洽性 7 条全过、数据有业务故事 |
| 交互真实 | 25 | 筛选/排序/分页/状态流转/反馈五项都真的生效 |
| 视觉规范 | 15 | 令牌一致、对齐正确、状态标签语义统一 |
| 零依赖可运行 | 10 | 断网可开、无报错 |
| 安全合规 | 15 | 全虚构数据、无外部接口、有人工复核 |

**评级**：≥90 可直接进需求评审 / 60–89 需人工补交互 / <60 视为不合格重生成。

## 效果对比指标（用于"效果验证"提交材料）

生成单个页面时，记录以下 6 个指标与人工基线对比：

| 指标 | 采集方式 |
|---|---|
| 首版可运行率 | 生成后未修改即可交互的页面占比 |
| 单页交付耗时 | 从下达需求到页面能演示（分钟） |
| 字段/条件覆盖率 | 页面已实现字段 ÷ 实体配方字段 |
| 交互命中率 | 通过 C 组 6 项检查的比例 |
| 设计令牌命中率 | 页面色值中属于令牌的比例 |
| 返工率 | 评审后需要人工补改的页面占比 |
