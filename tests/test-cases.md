## 六、自动化校验

`build/check_pages.py` 对全部产物自动执行 5 项检查：

1. **内嵌 JS 语法** —— 抽取 `<script>` 内容交由 Node `--check` 解析
2. **HTML 结构完整性** —— `html` / `head` / `body` 标签成对闭合
3. **零外部依赖** —— 正则扫描 `http(s)://`、常见 CDN 域名、`//cdn`、外链 `<script src>` / `<link href>` / `<img src>`，命中即失败
4. **免责声明** —— 检查产物是否含「示例数据」「虚构数据」「仅供演示」「脱敏」类声明
5. **代码量统计** —— 总行数、去注释后的有效代码行数、产物体积

脚本会自动在 `NODE_BIN` 环境变量、`PATH` 与常见安装位置中查找 node，未找到时降级为跳过 JS 检查并给出警告（不阻断其余检查）。

### 渲染期检测（`build/render_check.py`）

语法检查过了不代表页面真的能看。本脚本用**无头浏览器真实渲染**每个页面，再做 4 项检查：

1. **脏值扫描** —— 渲染后的 DOM 里是否出现 `undefined` / `NaN` / `null` / `[object Object]`
2. **横向溢出** —— 在 1280px 视口下 `scrollWidth - innerWidth` 是否 > 2px
3. **白屏检测** —— 可见正文去空白后是否少于 300 字
4. **控制台报错** —— 页面脚本是否抛错

无头浏览器通过固定 1280px 宽的 iframe 装载目标页面，读取其布局尺寸与 DOM，因此测的是**页面自身的布局**，不受宿主窗口宽度干扰。

## 七、实测发现并修复的缺陷

这一节是「效果验证」维度里最有说服力的部分 —— 它证明校验不是为了凑数，而是真的抓到了东西。

### 缺陷 1 · A1 列表页后 4 行「业务员」显示 `undefined`

- **现象**：渲染后第 7–10 行的业务员列为空字符串，实际输出 `undefined`
- **根因**：mock 数据用 `OWN[i]` 按索引取业务员，但 `OWN` 数组只有 6 个名字，而订单一共 14 行。
  另外 8 个数组（客户、状态、金额……）都是 14 个元素长，唯独业务员短了 —— **数组长度不一致**
- **修复**：改为 `OWN[i % OWN.length]`，6 名销售轮流承接 14 张订单，既补全了数据，也让「全部业务员」下拉保持 6 个选项不致冗长
- **发现方式**：`render_check.py` 的脏值扫描（**纯看源码极易漏掉**，因为代码本身没有语法错误）

### 缺陷 2 · A5 审批台在 1280px 下横向溢出 142px

- **现象**：内容宽 1422px，视口 1280px，整页出现横向滚动条
- **根因**：`.detail-b` 用了 `grid-template-columns:1fr 320px`。`1fr` 的隐式最小宽度是 `min-content`，
  而中栏里的明细表表头设了 `white-space:nowrap`，把 `min-content` 顶到了 426px，于是整页被撑开
- **修复**：弹性列改为 `minmax(0,1fr)` 并给栅格子项加 `min-width:0`，让中栏可以收缩、表格在自己的
  `.tbl-wrap{overflow:auto}` 里横向滚动；同时把三栏配比由 `340/320` 调为 `290/264`，
  并在 1400px 以下把 4 列键值对降为 2 列，避免长单号 `PR-2026-09-0173` 被折成三行
- **发现方式**：`render_check.py` 的横向溢出检测

### 缺陷 3 · 数字与日期列被折行

- **现象**：A1 的「订单日期」显示为 `2026-09-` / `17` 两行；A5 的物料编码 `MAT-2026-0012` 被折成三行
- **根因**：`.num` 类只设了 `font-variant-numeric:tabular-nums`（等宽数字），没有 `white-space:nowrap`。
  列宽不足时数字和日期照常换行
- **修复**：6 个页面统一补上 `td.num{white-space:nowrap}`；A5 的明细表加 `min-width` 交给容器滚动
- **已回写进 Skill**：`design-tokens.md` 4.5 节新增「数字列一律不折行」硬规则，
  `quality-checklist.md` 新增 D5 / D6 两条可执行检查动作

> **这三条缺陷暴露了同一个教训**：语法校验、外链扫描这类静态检查抓不到它们。
> 只有当页面被**真正渲染出来**、并且**在 1280px 这个验收宽度下量过尺寸**，问题才会现形。
> 因此我们把这个能力固化成了 `build/render_check.py`，而不是靠人肉点一遍。

## 八、跨技术栈适配实测（第二轮）

第一轮的 6 个页面都是**独立单文件 HTML**。这回答了"能不能生成页面"，但没回答评委真正会问的问题：
**把这个 Skill 拿到别人现有的项目里，还跑得通吗？**

为此做了第二轮实测：**同一套业务需求（A1 销售订单管理列表页）、同一套字段配方与 9 状态机，
在两个技术栈完全不同的真实项目里各生成一次。**

### 8.1 靶子的技术栈是全面错开的

| 维度 | 项目 A | 项目 B |
|---|---|---|
| 框架 | React 19 | Vue 3.5 |
| 语言 | JavaScript | TypeScript 5.6（`strict` + `noUnusedLocals`） |
| 状态管理 | Redux Toolkit | Pinia（setup 写法） |
| 构建 | CRA / webpack | Vite 6 |
| 样式 | 全局 CSS + CSS 变量 | CSS Modules（`<style module>`） |
| 目录 | `pages/` | `views/` |
| 命名 | PascalCase `.jsx` | kebab-case `.vue` |
| 已有设计令牌 | 无 | **有**（主色 `#2f6fed`） |

特意让项目 B **预先带一套自己的设计令牌**，用来测一个关键冲突：目标项目已有色值时，Skill 该服从谁。

### 8.2 用例

| # | 用例 | 输入 | 期望 | 实际 |
|---|---|---|---|---|
| TC-11 | React 19 项目内生成 | 项目路径 + "加一个销售订单管理页" | 按项目约定产出，构建通过 | 16 个文件 / 2804 行；`react-scripts build` 通过 |
| TC-12 | Vue 3 + TS 项目内生成 | 同上 | 按项目约定产出，类型与构建都过 | 8 个文件 / 1355 行；`vue-tsc` 零错误 + `vite build` 通过 |

### 8.3 两次产物：业务层一致，工程层各随其主

| 维度 | React 产物 | Vue 产物 | 结论 |
|---|---|---|---|
| 页面原型骨架（查询区/工具条/表格/分页） | 有 | 有 | **一致** |
| 字段配方（12 字段 + 金额精度） | 有 | 有 | **一致** |
| 状态机（9 状态 + 按钮可见性） | 有 | 有 | **一致** |
| Mock 数据规范（脱敏 + 自洽） | 有 | 有 | **一致** |
| 数字右对齐 / `nowrap` / 状态胶囊 | 有 | 有 | **一致** |
| 文件命名 | PascalCase | kebab-case | 各随项目 |
| 状态管理 | RTK slice | Pinia setup store | 各随项目 |
| 样式方案 | 全局 CSS 变量 | CSS Modules | 各随项目 |
| 主色变量 | `--brand` → 本项目 | `--brand-600` → 本项目 | 各自项目令牌 |

**这正是跨栈适配该有的样子**：变的是"长什么样、放在哪、怎么接线"，不变的是"业务逻辑与页面规矩"。

### 8.4 实测暴露的规范缺陷（已修复）

**缺陷 4 · Skill 旧版强制 React 用 `useState`，与真实项目脱节**

旧规范 `SKILL.md` 第 4 节写："React → 状态用 `useState`（不引第三方表格库）"。
但项目 A 的列表页数据由 Redux Toolkit 承载 —— 照规范做会产出跟项目完全接不上的代码。

- **修复**：删掉这条硬规定，改为**状态管理一律跟目标项目走**；`useState` 仅作"项目无状态库"时的兜底
- **新增 `references/stack-adaptation.md`**「技术栈适配协议」：四层取舍裁决 ——
  业务规范层服从 Skill、工程实现层服从项目、视觉令牌层整表替换、防坑规则层无条件保留
- **自检清单 20 → 23 项**，新增 3 条跨栈项（探测留存 / 令牌整表替换 / 目标栈编译级验证）

**缺陷 5 · 项目已有令牌时，硬套 Skill 色值会让页面"一眼看出是外来的"**

项目 B 的主色是 `#2f6fed`，Skill 默认是 `#2B5CFF`。两者接近但不同，混用后新页面与项目其它页面
在按钮、选中态、链接色上会出现可见色差，评审时会被指出。

- **修复**：确立"**整表替换**"原则 —— 项目已有令牌时，产物里只允许出现该项目的令牌变量，
  零 Skill 原色值残留。映射方法见 `stack-adaptation.md` 第 2.1 节

### 8.5 环境坑（已写入规范第 4.2 节）

| 坑 | 现象 | 解法 |
|---|---|---|
| Windows 显示缩放 | 传 `--window-size=1280` 实际只得到 1024 CSS px，测出**假的**横向溢出 | 加 `--force-device-scale-factor=1`，或改用同源 iframe 探测 |
| Vite dev server 截图挂死 | Chrome `--screenshot` 永不返回 | HMR 的 WebSocket 长连接让虚拟时间永不空闲 → 改用 `vite preview` 静态服务 |
| Chrome 参数路径 | `--user-data-dir=/c/Users/...` 被忽略，请求转发给用户正在用的 Chrome | 传 Windows 路径 `C:/Users/...` |
